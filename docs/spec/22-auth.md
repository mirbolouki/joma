# ۲۲ — ورود، ثبت‌نام، بازیابی رمز

> **قرارداد سند مادر:** `۴٫۱` · `۱۳٫۲`: «ورود امن و کم‌خطا: **فرم‌های واضح، خطای نزدیک فیلد، اعلام وضعیت عملیات**.»
> **هشدار امنیتی:** `۸٫۲` (SEC-01) · `FA-19` — این صفحه **دربارهٔ زیبایی نیست**، دربارهٔ درست‌بودن است.

---

## ۱) مانع امنیتی که پیش از هر طراحی باید حل شود

> ### 🔴 `۸٫۲` و `FA-19`
>
> «در مسیر بازیابی رمز، **تغییر رمز بدون اثبات مالکیت حساب** گزارش شده است.»
> «دربارهٔ سورس محلی، یافته مستند گزارش شده؛ دربارهٔ فعال‌بودن همان نقص روی هر استقرار عمومی، **تأیید مستقل نداریم**.»
>
> و در بازرسی: `FA-19` — «تب «فراموشی» روی سطح عمومی است، در حالی که مسیر بازیابی رمز نقص اثبات مالکیت دارد.» — **بلوکر امنیتی**.

### تصمیم‌های این سند

| # | تصمیم | دامنه |
|---|---|---|
| ۱ | **دکمهٔ «رمزت را فراموش کردی؟» تا اصلاح `SEC-01` نمایش داده نمی‌شود.** | رابط ورود |
| ۲ | مسیر `/recover` **در محصول نیست**. | مسیریابی |
| ۳ | اگر کاربر بدون آن مسیر، در بن‌بست می‌ماند → متن: «برای بازیابی رمز، با پشتیبانی تماس بگیر.» + لینک پشتیبانی | رابط ورود |
| ۴ | `۸٫۲` صریح گفته رسیدگی «**جدا از بازطراحی ظاهری**، با مجوز مشخص» انجام شود. **طراحی مسیر در §۴ نوشته شد**، ولی **ساختش مشروط به اصلاح `SEC-01` است.** | §۴ (طراحی) · ساخت: پس از بک‌اند |

**دلیل:** طراحی یک مسیر بازیابی «خوش‌ظاهر» روی منطقی که مالکیت را اثبات نمی‌کند، نقص را تجاری‌تر می‌کند، نه برطرف. این صفحه **باید منتظر بک‌اند بماند**.

**`[تصمیم]` طراحی مسیر، در §۴ همین فایل **نوشته شد** — ولی **ساختش** تا تأیید بک‌اند متوقف است. طراحی، منتظر بک‌اند نمی‌ماند؛ ساخت، می‌ماند.

## ۲) صفحهٔ ورود

```
        [کاشی جغد + جوما]
        «خوش برگشتی.»
        «از همان‌جایی که بودی ادامه بده.»

        [نام کاربری]
        [رمز عبور]
        [ورود]

        [رمزت را فراموش کردی؟]   ← نمایش داده نمی‌شود (§۱)
        «حساب نداری؟ ثبت‌نام کن»
```

### ۲.۱ فرم

| فیلد | قاعده |
|---|---|
| نام کاربری | `autocomplete="username"` · `autofocus` · بدون محدودیت کاراکتر در فرانت |
| رمز عبور | `type="password"` + دکمهٔ نمایش/پنهان · `autocomplete="current-password"` |
| دکمه | `.btn.primary` تمام‌عرض |

**`[تصمیم]` دکمهٔ نمایش رمز، ایموجی 👁 نیست** — آیکون SVG با `aria-label` «نمایش رمز» / «پنهان‌کردن رمز».

**ترتیب کلید:** `Tab` → نام کاربری → رمز → نمایش → ورود. `Enter` در هر فیلد → ارسال.

**`autocomplete` درست** برای پرکردن مدیریت رمز مرورگر — یک راه امن‌شدن بدون هیچ هزینه.

### ۲.۲ خطا — «خطای نزدیک فیلد» (`۱۳٫۲`)

| خطا | محل | متن |
|---|---|---|
| نام کاربری یا رمز غلط | **زیر فرم، نه زیر یک فیلد** | «نام کاربری یا رمز درست نیست. دقت کن یا با پشتیبانی تماس بگیر.» |
| فیلد خالی | زیر همان فیلد | «نام کاربری را بنویس.» / «رمز را بنویس.» |
| قطع اتصال | نوار بالای فرم | «اتصالت قطع است. دوباره امتحان کن.» |
| سرور خطا | نوار بالای فرم | «ورود انجام نشد. چند لحظه بعد دوباره امتحان کن.» |
| تلاش زیاد | زیر فرم | «تلاش‌های زیادی انجام شد. چند دقیقه صبر کن.» + زمان از بک‌اند |

> ### 🔴 چرا خطای «نام کاربری یا رمز غلط» **یک پیام مشترک** است
>
> جدا کردن «این نام کاربری وجود ندارد» از «رمز غلط است»، به مهاجم می‌گوید کدام نام کاربری‌ها معتبرند.
> این یک قاعدهٔ امنیتی است، ولی **متن آن باید انسانی باشد** — نه «Authentication failed».
>
> **زیر فرم، نه زیر فیلد:** چون خطا متعلق به هیچ‌کدام از دو فیلد تنها نیست.

**قاعده:** رمز عبور **هرگز** در متن خطا تکرار نمی‌شود.

### ۲.۳ اعلام وضعیت عملیات (`۱۳٫۲`)

| حالت | نمایش |
|---|---|
| در حال ارسال | دکمه `disabled` + «در حال ورود…» + نشانگر |
| موفق | هدایت به `/home` |
| ناموفق | دکمه آزاد + خطا |

**`[تصمیم]` دکمهٔ ورود در حین ارسال قفل می‌شود** — جلوگیری از ارسال دوباره.

### ۲.۴ مسیرهای فرعی

| عنصر | قاعده |
|---|---|
| «حساب نداری؟ ثبت‌نام کن» | لینک ساده، نه دکمه |
| «دربارهٔ جوما» | لینک به `/about` |
| بازگشت به لندینگ | لوگو |

**`[تصمیم]`** `FA-18` نشان داد لندینگ **سه مسیر ورود موازی** داشت. در این صفحه، **دو** راه وجود دارد: ورود و ثبت‌نام. نه بیشتر.

## ۳) صفحهٔ ثبت‌نام

`[تصمیم مالک — نسخهٔ ۱۰]` «صفحهٔ ثبت‌نام مطابق برنامهٔ اصلی باشد» و فرم کامل شود:

```
┌ ستون کنار ─────────┐  ┌ کارت اصلی ────────────────────────────────┐
│ [کاشی جوجهٔ من]    │  │ «ساخت حساب جومای من»        [ورود | ثبت‌نام | فراموشی]│
│ «همراه تو، قدم‌به‌قدم»│  │ «با پذیرش قوانین، حساب کاربری خود را می‌سازید.»      │
│ توضیح کوتاه        │  ├────────────────────────────────────────────┤
│ «بازگشت به معرفی»  │  │ [نام]            [نام خانوادگی]            │
└────────────────────┘  │ [نام کاربری]     [شماره موبایل]            │
                        │ [ایمیل]          [رمز عبور]                 │
                        │ [تکرار رمز عبور] [کد امنیتی]                │
                        │                  [درخواست کد امنیتی]        │
                        │ ☑ قوانین و مقررات و سیاست حفظ حریم خصوصی را │
                        │   خوانده‌ام و می‌پذیرم.                      │
                        │ [        ساخت حساب جدید        ]            │
                        │ «قبلاً حساب ساختی؟ وارد شو»                 │
                        └────────────────────────────────────────────┘
```

| فیلد | قاعده |
|---|---|
| نام / نام خانوادگی | متن آزاد؛ برچسب **داخل کادر** (طرح مرجع) |
| نام کاربری | ۳ تا ۲۰ کاراکتر · بررسی زندهٔ آزادبودن (§۳.۲) |
| شماره موبایل / ایمیل | برای **بازیابی حساب** و **پشتیبانی**؛ هرگز برای تبلیغ — همین جمله زیر فرم نوشته می‌شود |
| رمز عبور + تکرار | نوار قدرت رمز (§۳.۳) + بررسی تطابق دو رمز (§۳.۴) |
| کد امنیتی + «درخواست کد امنیتی» | دکمهٔ درخواست، برچسبش به «ارسال دوباره» تغییر می‌کند؛ اعتبار ۱۵ دقیقه |
| تیک قوانین | **الزامی**؛ تا تیک نخورد، دکمهٔ ساخت حساب خطای نزدیک فیلد می‌دهد. متن با دو پیوند به «قوانین و مقررات» و «حریم خصوصی» |
| دکمهٔ اصلی | «ساخت حساب جدید» — تمام‌عرض |

> ### 🔴 ثبت‌نام **هیچ فیلد نقشی ندارد** — به هیچ شکلی
>
> `[اصلاح مالک — نسخهٔ ۱۱]` «توی ثبت‌نام نقش نمی‌گرفتیم! کاربر می‌تواند نقش مدیر یا مشاور به خودش بدهد.» → **درست است و خطرناک.**
>
> | قاعده | تصمیم |
> |---|---|
> | فیلد نقش در ثبت‌نام | 🔴 **وجود ندارد** — نه کشویی، نه «سایر»، نه حتی به‌عنوان «درخواست» |
> | نقش حساب تازه | **همیشه `member` (کاربری)** — تصمیم بک‌اند، نه ورودی کاربر |
> | ارتقای نقش | **فقط از مسیر مدیریت** (`24-roles.md` §۵) — مدیر می‌دهد؛ کاربر نمی‌گیرد |
> | اگر کاربر نقش بالاتری بخواهد | در پروفایل، تنها یک جملهٔ راهنما: «نقش‌ها را مدیر مجموعه می‌دهد؛ اگر لازم داری، با پشتیبانی بگو» — **بدون فیلد ورودی** |
> | چرا؟ | هر ورودی‌ای که به نقش وصل باشد، یک **حفرهٔ دسترسی** است: با یک درخواست `POST` دست‌کاری‌شده، حساب «مدیر» ساخته می‌شود. سطح حمله را خودمان نمی‌سازیم |
>
> **قاعدهٔ کلی برای هر فرم ثبت‌نام:** فیلدهای فرم دقیقاً همان‌هایی هستند که هویت و امنیت حساب را می‌سازند (نام، نام کاربری، موبایل/ایمیل، رمز، کد، رضایت). هر فیلدی که **مجوز** می‌دهد، از فرم‌های عمومی حذف است.

### ۳.۰.۱ **`[تصمیم مالک — نسخهٔ ۱۵]` ثبت‌نام گام‌به‌گام است**

> مالک: «می‌شه ثبت‌نام هم مثل فراموشی رمز مرحله‌به‌مرحله اطلاعات بگیره؟ ولی نه اینکه بگه اسمتو بگو حالا فامیلی؛ بخش‌های مربوط به هم را با هم بگیره.»

**پنج گام، هر گام یک «دستهٔ مربوط به هم»** — نه یک فیلد در هر گام:

| گام | عنوان | فیلدها | چرا این‌ها با هم |
|---|---|---|---|
| **۱** | خودت را معرفی کن | نام · نام خانوادگی · **جنسیت** | سه چیز مربوط به «هویت کاربر» |
| **۲** | شغلت چیست؟ | **شغل — دراپ‌داون** | یک تصمیم مستقل و مهم (آمار و تنظیم تجربه) |
| **۳** | حساب کاربری‌ات | نام کاربری (+ بررسی زنده) · رمز · تکرار رمز | سه چیز مربوط به «حساب» |
| **۴** | راه‌های تماس | موبایل · ایمیل | دو کانال بازیابی |
| **۵** | یک قدم مانده | خلاصهٔ اطلاعات · کد پشتیبانی · تیک قوانین · ساخت حساب | تأیید نهایی — کاربر یک‌بار همه را می‌بیند |

| قاعده | تصمیم |
|---|---|
| نشانگر گام | پنج نقطه (`۱ ✓`) + «گام ۳ از ۵» — مثل بازیابی رمز |
| دکمه‌ها | «ادامه» + «قبلی» (گام ۱ «قبلی» ندارد) |
| اشتباه | فقط فیلدهای همان گام بررسی می‌شوند؛ پیام کوتاه زیر صفحه |
| قبلی | داده‌های گام‌های قبل **حفظ می‌شوند** (کاربر دوباره نمی‌نویسد) |
| گام ۵ | خلاصهٔ خوانا: نام · جنسیت · شغل · نام کاربری · موبایل — و کد پشتیبانی |
| 🔴 ممنوع | گامی که فقط یک فیلد دارد ولی با گام قبل یکی است (مثل گام جدا برای فامیلی) |

### ۳.۰.۲ **`[تصمیم مالک — نسخهٔ ۱۵]` شغل و جنسیت — مطابق فرم اصلی**

> مالک: «کاربر اون‌جا شغل را از دراپ‌داون انتخاب می‌کرد ولی اینجا اصلا فیلد شغل نیست… جنسیت هم سوال نمی‌شه… فیلدها را منطبق کن. بعداً می‌خوام بگم ۱۰۰ کارمند دارم، ۱۰ پزشک، ۳۰ دانشجو.»

| فیلد | شکل | مقدار | چرا |
|---|---|---|---|
| **شغل** | دراپ‌داون گروه‌بندی‌شده (`<optgroup>`) | **کد + عنوان از بک‌اند** — فهرست پیشنهادی سند در §۳.۷ | «۱۰۰ کارمند · ۱۰ پزشک · ۳۰ دانشجو» فقط با فیلد **ساخت‌یافته** شمرده می‌شود؛ متن آزاد این را نمی‌دهد |
| **جنسیت** | سه قرص (زن · مرد · **ترجیح می‌دهم نگویم**) | کد از بک‌اند | آمار تجمیعی؛ گزینهٔ سوم احترام است، نه دورزدن |

**قاعده‌های سخت:**
1. 🔴 **شغل هرگز متن آزاد نیست** — وگرنه «کارمند» با ده املای مختلف ثبت می‌شود و آمار بی‌معنا می‌شود.
2. 🔴 **فهرست شغل از بک‌اند می‌آید.** اگر بک‌اند فهرست نداشت، فرانت فهرست پیشنهادی §۳.۷ را **نشان می‌دهد** ولی انتخاب را به کد نمی‌نگارد و به بک‌اند «حدس» نمی‌فرستد.
3. **پرسش «چرا می‌پرسیم» همیشه زیر فیلد هست** — «برای آمار تجمیعی و تنظیم تجربه، نه برای فروش داده».
4. **هیچ‌کدام اجباریِ سخت نیستند مگر با تأیید بک‌اند** — اگر بک‌اند نپذیرد، جریان ثبت‌نام نباید بشکند؛ پیام می‌دهد و از فیلد می‌گذرد.
5. **در گزارش‌های عمومی هیچ‌وقت به یک نفر وصل نمی‌شوند** (`۲۶`).

### ۳.۱ سازوکار کد ثبت‌نام

`۴٫۱`: «بررسی نام کاربری و **سازوکار کد ثبت‌نام قابل‌پیکربندی**».

| حالت | رابط |
|---|---|
| کد غیرفعال | فیلد نمایش داده نمی‌شود |
| کد فعال | فیلد با برچسب «کد ثبت‌نام» + توضیح «کد را از جایی که جوما را به تو معرفی کرده گرفته‌ای» |

**`[تصمیم]`** فعال/غیرفعال بودن از بک‌اند می‌آید. فرانت تصمیم نمی‌گیرد.

> ### 🔴 `[تصمیم مالک — اتحاد شاخه‌ها]` کد ثبت‌نام = **قفل دستی**، نه پیامک
>
> «پیامک سیستم وصل نیست. کد به کاربر داده نمی‌شود.» پس فرانت **هرگز نمی‌نویسد** «کد برایتان پیامک می‌شود» و هیچ وعدهٔ ارسال خودکار نمی‌دهد.
>
> | عنصر | متن و رفتار |
> |---|---|
> | دکمهٔ کنار فیلد کد | **«دریافت کد از پشتیبانی»** — نه «ارسال کد»، نه «درخواست کد امنیتی» |
> | پس از زدن دکمه | پنل کوچک با دو کانال: **پیامک** و **پیام‌رسان بله**، هر دو با شمارهٔ **۰۹۹۶۷۹۷۹۴۷۱** + «کپی شماره» + متن آماده: «سلام، برای ثبت‌نام در جوما کد می‌خواهم.» |
> | متن زیر فیلد | «کد ثبت‌نام را از پشتیبانی می‌گیری — پیامک یا بله به همین شماره. معمولاً کمتر از یک روز کاری.» |
> | همان قانون در **بازیابی رمز** | مسیر §۴ هم تا وقتی اثبات مالکیت روشن نشده، فقط با پشتیبانی کار می‌کند — همان شماره |
> | 🔴 ممنوع | «کد پیامک شد» · «ارسال دوباره» · شمارش معکوس ۱۵ دقیقه‌ای برای کدی که ارسال نمی‌شود |

### ۳.۷ فهرست پیشنهادی شغل (تا وقتی بک‌اند فهرست رسمی بدهد)

| گروه | عنوان‌ها |
|---|---|
| اداری و مدیریت | کارمند · مدیر یا سرپرست · کارآفرین و صاحب کسب‌وکار |
| سلامت | پزشک · پرستار · روان‌شناس یا مشاور · سایر کادر درمان |
| آموزش | معلم · استاد دانشگاه · مربی |
| دانشجو و دانش‌آموز | دانشجو · دانش‌آموز · طلبه |
| فنی و آزاد | مهندس · برنامه‌نویس · هنرمند یا طراح · فریلنسر |
| خانه و خانواده | خانه‌دار · در مرخصی یا جویای کار · بازنشسته |
| سایر | سایر |

**`[نیاز بک‌اند — `N7`]` پرسش‌های بسته:** ① آیا جدول کاربران **ستون شغل** و **جنسیت** دارد؟ (فرم اصلی جوما شغل را داشت، پس احتمالاً دارد) ② نام دقیق ستون‌ها چیست؟ ③ مقادیر مجاز هرکدام کدام‌اند (کد/عنوان)؟ ④ آیا شغل و جنسیت باید **الزامی** باشند یا اختیاری؟ تا پاسخ، فرانت فهرست پیشنهادی بالا را نشان می‌دهد و جریان را نمی‌شکند.

| در حال بررسی | نشانگر کوچک کنار فیلد |
| آزاد | ✅ «این نام آزاد است.» |
| گرفته | ❌ «این نام قبلاً انتخاب شده. یکی دیگر امتحان کن.» |
| کوتاه/بلند | «نام کاربری باید بین ۳ تا ۲۰ کاراکتر باشد.» |

**`[تصمیم]`** محدودیت طول **از بک‌اند** می‌آید و در متن خطا نوشته می‌شود. فرانت قاعده را از خودش نمی‌سازد (`۴٫۴`).

**تأخیر بررسی:** `400ms` پس از توقف تایپ. نه در هر کاراکتر.

### ۳.۳ اعتبارسنجی رمز

**`[تصمیم]` قواعد رمز از بک‌اند می‌آیند.** فرانت فقط نمایش می‌دهد:

```
قواعد رمز:                ← فهرست زنده، از بک‌اند
✅ حداقل ۸ کاراکتر
⬜ یک عدد
⬜ یک حرف بزرگ
```

**قاعده:** فهرست **پیش از** ارسال نمایش داده می‌شود، نه پس از خطا. کاربر باید بداند چه می‌خواهید.

**ممنوع:** قدرت‌سنج رنگی («ضعیف/قوی») اگر آستانه‌اش در فرانت تعریف شده باشد.

### ۳.۴ اعتبارسنجی «تکرار رمز»

**`[تصمیم]` نیازی به فیلد «تکرار رمز» نیست اگر دکمهٔ نمایش رمز وجود دارد.** یک فیلد با دکمهٔ نمایش، خطای کمتری از دو فیلد می‌سازد.

اگر بک‌اند این فیلد را لازم دارد، خطای «دو رمز یکسان نیستند» زیر فیلد دوم می‌آید و **هر دو** با `aria-invalid` علامت می‌خورند.

### ۳.۵ متن رضایت

`[نیازمند راستیآزمایی]` متن شرایط استفاده و حریم خصوصی موجود نیست (`۱۷٫۳`).
**تا آن زمان:** صفحهٔ ثبت‌نام **متن رضایت جعلی نسازد.** فقط یک خط:
«با ساخت حساب، [شرایط استفاده] و [حریم خصوصی] را می‌پذیری.»
و پیوندها تا آماده‌شدن متن، **غیرفعال** با برچسب «به‌زودی» — یا کل جمله حذف.

**`[تصمیم]`** کل جمله **حذف می‌شود** تا متن آماده باشد. ارجاع به سندی که وجود ندارد، بدتر از نبودن ارجاع است.

### ۳.۶ پس از ثبت‌نام موفق

`PD-005`: «خوش‌آمد کوتاه، معرفی «دانهٔ پرواز»، هدایت به برنامهٔ اول و **راهنمای تعاملی اختیاری**.»

```
[پوشش خوش‌آمد — یک صفحه، حداکثر دو جمله]
«خوش آمدی! یک تخم برایت داریم که با قدم‌هایت رشد می‌کند.»
[ساخت اولین برنامه]  [اول بگذار ببینم]
```

| قاعده | تصمیم |
|---|---|
| یک پوشش، نه تور پنج‌مرحله‌ای | `۱۳٫۴` — راهنما اختیاری است |
| «اول بگذار ببینم» → `/home` بدون برنامه | کاربر آزاد است |
| راهنمای تعاملی | در `/home` به‌عنوان کارت، قابل اجرا و قابل رد |
| هیچ ثبتی در خوش‌آمد | `۱۳٫۴` |
| راهنمای کاربر قدیمی ≠ تازه‌وارد | `۱۳٫۴` |

## ۴) صفحهٔ بازیابی رمز — طراحی کامل، **ساخت مشروط**

> ### 🔴 دو چیز را از هم جدا نگه دار
>
> | | وضعیت |
> |---|---|
> | **طراحی مسیر** | ✅ **تمام شد — همین بخش.** تا وقتی مبهم بماند، هر کسی چیزی از خودش می‌سازد |
> | **ساخت مسیر** | ⛔ **متوقف** تا بک‌اند **اثبات مالکیت** را درست کند (`SEC-01`) |
>
> **`[تصمیم]` قاعدهٔ بی‌استثنا:** اگر «فراموشی رمز» بدون اثبات مالکیت کار کند، **بدتر از نداشتنش** است.
> پس `OPEN-39` = «آیا بک‌اند اثبات مالکیت را دارد؟» و تا پاسخ «بله»، دکمه‌ای ساخته نمی‌شود.

### ۴.۰ وضعیت واقعی بک‌اند — **پاسخ روشن به پرسش مالک**

> مالک پرسید: «آیا فراموشی رمز عبور در بک‌اند نوشته شده؟ چطور کار می‌کند؟»

| پرسش | پاسخ |
|---|---|
| آیا در بک‌اند نوشته شده؟ | **نشانگر `SEC-01` در فایل‌های بک‌اند پیدا نشد** ⇒ وضعیتش روشن نیست. این اولین پرسش بستهٔ بعدی به نویسندهٔ بک‌اند است |
| آیا راه خودکار می‌شود؟ | **نه** — چون «ایمیل» و «پیامکِ محصولی» به‌تصمیم مالک در بک‌اند **وجود ندارند**. پس کد نمی‌تواند خودکار به کاربر برسد |
| پس چطور کار می‌کند؟ | **همان الگوی کد ثبت‌نام:** کد را **سرور** صادر می‌کند (یک‌بارمصرف، ۱۵ دقیقه، ۵ تلاش) و **پشتیبانی** آن را دستی تحویل می‌دهد (`۰۹۹۶۷۹۷۹۴۷۱` — پیامک یا بله) |
| امروز در رابط چه هست؟ | صفحهٔ «بازیابی رمز» با چهار گام **ساخته شده** (نمونه: صفحهٔ ۴)؛ تا وقتی بک‌اند endpoint تأیید کد را نداشته باشد، ساختنِ نهایی نمی‌شود |

**نیاز بک‌اند (کد `N4`):** یک endpoint که (الف) به ازای شناسهٔ معتبر کد یک‌بارمصرف بسازد، (ب) کد را **بدون** تحویل خودکار بپذیرد، (ج) پس از تغییر رمز همهٔ نشست‌ها را باطل کند.

### ۴.۱ اصل طراحی — فقط **یک** راه پذیرفته است

> **`[تصمیم]` اثبات مالکیت، فقط با چیزی که کاربر **از قبل** صاحبش است: کد یک‌بارمصرف به **ایمیل یا موبایل ثبت‌شدهٔ همان حساب**.**

| روش | حکم | چرا |
|---|---|---|
| **کد یک‌بارمصرف به کانال ثبت‌شده** | ✅ **تنها روش مجاز** | مالکیت را واقعاً اثبات می‌کند |
| سؤال امنیتی («نام اولین مدرسه») | ❌ ممنوع | جوابش را می‌شود حدس زد یا پیدا کرد |
| «آخرین فعالیتت چه بود؟» | ❌ ممنوع | برای همسایه و همکار قابل حدس است |
| **کد سیستم + تحویل دستی توسط پشتیبانی** | ✅ **مسیر فعلی محصول** | کد را **سرور** می‌سازد و می‌سنجد؛ پشتیبانی فقط حامل است. تا وقتی ایمیل و پیامک محصولی وصل نشده‌اند، تنها راه واقعی همین است |
| تأیید دستی هویت توسط پشتیبانی (بدون کد سرور) | ❌ ممنوع | پشتیبانی نمی‌تواند هویت را با اطمینان تشخیص دهد و هیچ ردّ سیستمی نمی‌ماند |
| ارسال رمز فعلی برای کاربر | ❌ **هرگز** | رمز در بک‌اند ذخیره نمی‌شود (باید هش باشد) |

 کد ۱۵ دقیقه اعتبار دارد.»

        ↓
گام ۲ — کد

### ۴.۳ قواعد سخت این مسیر

| # | قاعده | مقدار |
|---|---|---|
| **۱** | **پاسخ یکسان** در گام ۱ | همیشه — صفحهٔ «این حساب وجود ندارد» = لو دادن اطلاعات |
| **۲** | عمر کد | `۱۵ دقیقه` |
| **۳** | کد **یک‌بارمصرف** | پس از استفاده باطل می‌شود |
| **۴** | تعداد تلاش کد | `۵ بار` — بعد از آن کد باطل و کد تازه لازم است |
| **۵** | ارسال دوباره | `۶۰ ثانیه` فاصله، سقف `۵ بار در ساعت` |
| **۶** | سقف کلی | `[نیازمند تصمیم — OPEN-39]` — پیشنهاد: `۱۰ درخواست در ساعت برای هر شناسه` و `۳۰ برای هر IP` |
| **۷** | پس از تغییر رمز | **همهٔ نشست‌ها باطل می‌شوند** — کاربر باید از نو وارد شود |
| **۸** | اطلاع‌رسانی | پیام به همان کانال: «رمز حساب تو عوض شد. اگر این تو نبودی، فوراً به پشتیبانی بگو.» |
| **۹** | لاگ | هر درخواست، هر تأیید، هر شکست — با IP و زمان (`۱۶٫۷`) |
| **۱۰** | **متن پیام** | نه رمز جدید، نه لینک ورود خودکار، نه هیچ قابل‌حدس‌زدنی |
| **۱۱** | بدون لو دادن وجود حساب | در هیچ خطا و هیچ پیامی |
| **۱۲** | انقضای لینک (اگر لینک بود) | `۱۵ دقیقه` · یک‌بارمصرف · **اتصال به دستگاه، نه نشست** |

**`[تصمیم]` دربارهٔ عددها:** پیشنهاد طراحی‌اند، نه قانون. بک‌اند می‌تواند سخت‌گیرتر کند؛ **آسان‌تر نه**.

### ۴.۴ کاربری که هیچ کانال بازیابی ندارد

وضعیت واقعی: کاربرانی که با **کد پیامکی** ثبت‌نام کرده‌اند و ایمیل ندارند — اگر شماره‌شان عوض شود، راه بازگشت **ندارند**.

| تصمیم | مقدار |
|---|---|
| **۱ · در ثبت‌نام** | `[تصمیم]` پس از ثبت‌نام، یک بار از کاربر بخواه **یک کانال بازیابی** اضافه کند — **اجباری نباشد، ولی برجسته** |
| **۲ · در تنظیمات** | یک ردیف همیشه دیده می‌شود: «کانال بازیابی: ✅ موبایل ۰۹۱۲… · ➕ افزودن ایمیل» |
| **۳ · اگر نداشت** | دکمهٔ «فراموشی رمز» دیده می‌شود، ولی گام ۱ پیام متفاوتی می‌دهد: «برای این حساب راه بازیابی تنظیم نشده. با پشتیبانی تماس بگیر.» |
| **۴ · پشتیبانی** | `[نیازمند تصمیم — OPEN-12/39]` رویهٔ تأیید هویت انسانی — **و توصیه: سخت‌گیرانه، نه آزمایشی** |

**`[تصمیم]` و یک نکتهٔ صادقانه:** پشتیبانی‌ای که با یک تماس، رمز هر کسی را عوض کند، **همان نقص `SEC-01` را به میز پشتیبانی منتقل کرده** است. اگر بک‌اند راه فنی ندارد، بهتر است این مسیر **نباشد** تا اینکه به یک انسان گره بخورد.

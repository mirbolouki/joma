> **وضعیت این فایل:** متنِ تحویل‌شده توسط مالک محصول (سند مادر جوما، نسخهٔ ۰٫۲)، که از گفت‌وگو به مخزن منتقل شده است تا مرجع پایدار و قابل‌ارجاع باشد.
> **قاعدهٔ ویرایش:** این فایل **متن مالک** است. هر تغییر معنایی باید در گفت‌وگو تصویب و سپس با ثبت در `docs/01-decision-register.md` اعمال شود. تنها تغییرهای اعمال‌شده در این نسخه، **قالب‌بندی** (جدول‌بندی و تیتربندی) و افزودن یادداشت‌های `[یادداشت مخزن]` است.
> **دو نکتهٔ شکلی:** (۱) شمارهٔ «۱۰٫۴» در متن اصلی دو بار آمده؛ برای حفظ شماره‌های خودِ مالک، به «۱۰٫۴-الف» (مرجع رنگ) و «۱۰٫۴-ب» (نام‌گذاری فرهنگی) تفکیک شده است. (۲) یک مقدار رنگ در متن ارسالی ناقص رسیده که در جای خود علامت‌گذاری شده است.

## بخش اول — اعتبار، هدف و شیوهٔ استفاده از سند

### ۱.۱ هدف سند

این سند چهار موضوع را از یکدیگر جدا و سپس به هم متصل می‌کند:

1. **جوما اکنون چه قابلیت‌هایی دارد؟**
2. **داده‌ها در بک‌اند چگونه ثبت، پردازش و نمایش داده می‌شوند؟**
3. **در نسخهٔ جدید، کاربر چه تجربه‌ای خواهد داشت؟**
4. **کدام قابلیت‌ها و قواعد هنوز نیازمند تصمیم، طراحی یا پیاده‌سازی‌اند؟**

این سند، جایگزین سورس معتبر، مستندات تخصصی موتورهای محاسباتی یا تست اجرایی نیست؛ بلکه مرجع هماهنگی محصول و توسعه است.

### ۱.۲ مبنای اطلاعات

اطلاعات وضعیت موجود از این منابع گردآوری شده است:

- آخرین گزارش ایجنت با عنوان «مرجع یکپارچهٔ داده، جریان ثبت و منطق بک‌اند JOMA».
- گزارش‌های اصلاحی معماری و موازی‌کاری.
- کدهای دموهای 7A و 7B که در گفت‌وگو ارائه شده‌اند.
- تصمیم‌های صریح مالک محصول در ادامهٔ گفت‌وگو.

**محدودیت اعتبار:** نگارندهٔ این سند، سورس PHP و استقرار زنده را مستقلاً اجرا نکرده است. بنابراین عبارت «وضعیت موجود» در این سند، به معنی **رفتار گزارش‌شده از سورس بررسی‌شده** است؛ نه تأیید نهایی تمام رفتارهای سایت زنده.

### ۱.۳ وضعیت‌های مورد استفاده

| برچسب | معنی |
|---|---|
| **موجود** | در سورس فعلی گزارش شده است. |

| **پیشنهادی** | راهکار طراحی یا فنی برای بررسی و تصویب است. |
| **باز** | هنوز تصمیم نهایی ندارد. |
| **نیازمند راستی‌آزمایی** | شواهد اجرایی یا مرجع دقیق آن کامل نیست. |

**هیچ پیشنهاد این سند نباید صرفاً به دلیل نوشته‌شدن، تصمیم مصوب تلقی شود.**

### ۱.۴ مجوز اجرا

هر مرحلهٔ اجرا به محدودهٔ مشخص، برنامهٔ تست و تأیید جداگانه نیاز دارد.

## بخش دوم — تعریف محصول و مخاطبان

### ۲.۱ جوما چیست؟

جوما یک محصول **برنامه‌ریزی، ثبت واقعیت روزانه و شناخت الگوهای شخصی** است.

تعریف پیشنهادی ارزش محصول:

***جوما کمک می‌کند برنامه‌ای متناسب با زندگی‌ات بسازی، آنچه واقعاً انجام داده‌ای و حالی که داشته‌ای را ثبت کنی و با مرور این داده‌ها، خودت و الگوهای روزهایت را بهتر بشناسی.***

جوما صرفاً یک فهرست کار، یک بازی مراقبت از پرنده یا مجموعه‌ای از نمودارها نیست. این اجزا باید در خدمت یک چرخهٔ مشترک باشند:

**برنامه‌ریزی متناسب → زندگی و فعالیت واقعی → ثبت صادقانه → شناخت الگوها → تنظیم آگاهانه‌تر برنامه**

### ۲.۲ مخاطبان مصوب

**مخاطب فعلی**

- بزرگسالان فارسی‌زبان؛
- بازار اولیه داخل ایران؛
- کاربران مستقل؛
- مراجعانی که با همراهی یک متخصص یا همراه مجاز از جوما استفاده می‌کنند.

**اتصال به همراه، پیش‌شرط استفاده از جوما نیست.**

**مخاطب آینده**

ورود نوجوانان در نسخهٔ بعدی در چشم‌انداز محصول قرار دارد.

این توسعه فقط تغییر رنگ و لحن نیست و پیش از اجرا به بررسی جداگانه نیاز دارد:

- رضایت و حریم خصوصی؛
- محتوای مناسب سن؛
- حدود نقش والد یا همراه؛
- شیوهٔ پیام‌رسانی و پاداش؛
- ارزیابی اثر تجربهٔ مراقبت از همراه مجازی.

بازارهای خارج از ایران نیز در آینده قابل‌بررسی‌اند، اما قواعد منطقهٔ زمانی، زبان و الزامات آن‌ها هنوز مصوب نیست.

### ۲.۳ هدف تجربه در طول زمان

| بازه | نتیجهٔ مطلوب |
|---|---|
| **اولین استفاده** | کاربر بفهمد جوما چیست و قدم بعدی‌اش کدام است. |
| **هفتهٔ اول** | استفاده راحت و دوست‌داشتنی باشد و کاربر برای ثبت‌های بعدی انگیزه پیدا کند. |
| **پس از جمع‌شدن دادهٔ کافی** | کاربر شناخت قابل‌فهمی از الگوهای رفتاری و همراهی حال و فعالیت‌هایش به دست آورد. |

جوما نباید برای روز مشخصی وعدهٔ کشف معتبر بدهد؛ کفایت داده به کیفیت، تعداد و توزیع ثبت‌ها وابسته است.

### ۲.۴ معیار موفقیت محصول

موفقیت با این موارد سنجیده می‌شود:

- انجام کار اصلی با سردرگمی و خطای کمتر؛
- ثبت معتبر و صادقانه؛
- بازگشت داوطلبانه برای استفادهٔ معنادار؛
- مفیدبودن گزارش‌ها و بینش‌ها از نگاه کاربر؛
- شناخت تدریجی الگوهای شخصی؛
- احساس همراهی، بدون فشار و گناه.

**افزایش زمان حضور در صفحه، به‌تنهایی معیار موفقیت نیست.** کاربر باید بتواند کارش را انجام دهد و با رضایت به زندگی واقعی برگردد.

## بخش سوم — معماری فعلی بک‌اند

### ۳.۱ تصویر کلی

طبق آخرین ممیزی، جوما یک اپلیکیشن **PHP فرم‌محور** است.

ساختار اصلی:

```text
صفحه و فرم کاربر
        ↓
دریافت درخواست در PHP
        ↓
کنترل ورود، مجوز، مالکیت و اعتبار داده
        ↓
توابع دامنه و ذخیره‌سازی
        ↓
موتور موفقیت و لایه‌های تحلیلی
        ↓
HTML یا دادهٔ آمادهٔ نمایش
        ↓
مرورگر
```

**فناوری‌های گزارش‌شده**

- PHP رویه‌ای و تابع‌محور؛
- HTML، CSS و JavaScript برای نمایش و تعامل؛
- بدون چارچوب PHP یا Composer در هستهٔ گزارش‌شده؛
- Chart.js محلی برای رسم نمودارها؛
- توابع جلالی موجود در بک‌اند؛
- فونت فارسی Vazirmatn در طراحی فعلی؛
- فرم‌های POST و فیلترهای GET.

**API**

هستهٔ فعلی REST API عمومی برای همهٔ قابلیت‌ها ندارد.

تنها endpoint مشخص گزارش‌شده:

`api/username.php` برای بررسی در دسترس بودن نام کاربری.

بنابراین فرانت جدید نباید از ابتدا فرض کند تمام عملکردها باید به یک SPA یا REST API تازه تبدیل شوند. **رندر PHP و فرم‌های موجود نیز می‌توانند قرارداد «فرانت نمایش‌دهندهٔ بک‌اند» را تأمین کنند.**

### ۳.۲ محل مسئولیت‌ها

| مسئولیت | مرجع فعلی گزارش‌شده |
|---|---|
| مسیریابی صفحات | `index.php` |
| نشست، بارگذاری اولیه و تنظیمات | `includes/bootstrap.php` و اجزای مرتبط |
| کنترل دسترسی و اعتبارسنجی‌های مشترک | `includes/helpers.php` |
| فعالیت، برنامه، دوره و ثبت‌ها | `functions/joma.php` |
| تقویم جلالی | `includes/jalali.php` |
| موتور موفقیت | `functions/success.php` |
| تحلیل‌های اصلی | `includes/analytics.php` |
| گزارش تحلیلی R1/R2 | `functions/analytics_reports.php` |
| هم‌مسیر | `functions/hammasir.php` |
| ذخیره‌سازی | `includes/store.php` و ذخیره‌سازی مستقل هم‌مسیر |

این فهرست، نقشهٔ مسئولیت است؛ شماره‌خط‌ها و نسخهٔ دقیق فایل‌ها باید در پیوست فنیِ متصل به سورس ثابت شوند.

### ۳.۳ دو حالت ذخیره‌سازی موجود

**حالت فایل**

دادهٔ هسته در یک فایل JSON نگهداری می‌شود.

**محدودیت گزارش‌شده:** مسیر نوشتن هسته قفل هماهنگ ندارد؛ بنابراین نوشتن هم‌زمان می‌تواند به ازدست‌رفتن تغییرات منجر شود.

**حالت MySQL**

ذخیره‌سازی با mysqli و کوئری‌های پارامتری انجام می‌شود.

**محدودیت گزارش‌شده:** عملیات چندمرحله‌ای هسته، در همهٔ مسیرها داخل تراکنش قرار ندارند. بررسی تکراری‌نبودن و سپس درج، در برابر درخواست‌های هم‌زمان تضمین کامل ایجاد نمی‌کند.

**هم‌مسیر**

برای برخی عملیات خود از قفل و نوشتن اتمیک در حالت فایل و سازوکار قفل/تراکنش در MySQL استفاده می‌کند.

**نتیجه:** وجود یک روش امن در هم‌مسیر، به معنی ایمن‌بودن خودکار همهٔ مسیرهای هسته نیست.

## بخش چهارم — قابلیت‌های فعلی برنامه

### ۴.۱ حساب کاربری و صفحات عمومی

| بخش | قابلیت موجود |
|---|---|
| معرفی جوما | صفحهٔ عمومی معرفی محصول و مسیر ورود |
| ثبت‌نام | دریافت مشخصات، اعتبارسنجی، بررسی نام کاربری و سازوکار کد ثبت‌نام قابل‌پیکربندی |
| ورود | بررسی اطلاعات حساب و ایجاد نشست |
| بازیابی رمز | مسیر موجود است، اما نقص امنیتی جدی دربارهٔ اثبات مالکیت گزارش شده است |
| خروج | پایان نشست |
| درباره | محتوای رسمی معرفی و فلسفهٔ محصول |
| پشتیبانی | کانال‌های عمومی ارتباطی |
| پروفایل | مشاهدهٔ اطلاعات حساب |
| تنظیمات | ویرایش مشخصات مجاز، کارت فشرده و ترجیح اعلان |

**اعلان:** ذخیرهٔ ترجیح اعلان گزارش شده، اما سازوکار واقعی ارسال اعلان، پیامک یا ایمیل در هستهٔ بررسی‌شده وجود ندارد.

### ۴.۲ دوره‌ها و برنامه‌ها

**دوره**

دوره، ظرف زمانی ماهانه بر اساس تقویم جلالی است.

کاربر می‌تواند:

- دوره بسازد؛
- دوره را انتخاب کند؛
- جزئیات و آمار آن را ببیند؛
- برنامهٔ مرتبط را مدیریت کند.

**برنامه**

برنامه مشخص می‌کند:

- چه فعالیت‌هایی پیگیری شوند؛
- تناوب هر فعالیت چیست؛
- هدف و واحد آن چیست؛
- اهمیت یا وزن آن چگونه در محاسبات لحاظ شود.

**چرخهٔ وضعیت گزارش‌شده**

| وضعیت فعلی | انتقال‌های مجاز |
|---|---|
| DRAFT | PLANNING یا ARCHIVED |
| PLANNING | RUNNING، DRAFT یا ARCHIVED |
| RUNNING | ARCHIVED |

برای ورود به مراحل لازم، حداقل فعالیت و سایر گاردهای موجود بررسی می‌شوند.

**برنامهٔ در حال اجرا قفل محتوایی دارد.** افزودن یا تغییر فعالیت نباید از طریق ویجت‌های تازه، این قفل را دور بزند.

### ۴.۳ اسنپ‌شات فعالیت در برنامه

فعالیتِ داخل برنامه، فقط یک اشاره به نسخهٔ زندهٔ کتابخانه نیست؛ مشخصات آن در زمان افزودن ثبت می‌شود.

برای مثال:

- نام؛
- نوع داده؛
- واحد؛
- هدف؛
- تناوب؛
- وزن؛
- استیکر و رنگ.

بنابراین اگر کاربر بعداً فعالیت کتابخانه را ویرایش کند، **هدف و مشخصات تاریخی برنامه‌های قبلی خودکار تغییر نمی‌کنند**.

این رفتار برای حفظ معنی گزارش‌های گذشته ضروری است و باید در فرانت جدید قابل‌فهم باشد.

### ۴.۴ کتابخانهٔ فعالیت‌ها

کاتالوگ رسمی گزارش‌شده شامل **۱۰۷ فعالیت** است:

- ۴۵ فعالیت پایه؛
- ۳۵ فعالیت مرتبط با مسیر زوج‌درمانی؛
- ۲۷ فعالیت مرتبط با مسیر طرحواره.

امکانات موجود:

- مرور و فیلتر؛
- ساخت فعالیت شخصی؛
- ویرایش مشخصات مجاز؛
- فعال یا غیرفعال‌کردن؛
- انتخاب برای برنامه.

**انواع داده**

- DURATION: مدت‌زمان؛
- NUMERIC: مقدار عددی؛
- BOOLEAN: انجام/عدم انجام؛
- RATING: امتیاز خودگزارشی.

واحدها می‌توانند دقیقه، ساعت، لیوان، تعداد، مرتبه، امتیاز یا بدون واحد باشند.

**قواعد هدف**

قواعد نوع، واحد، مقدار، گام ورودی و تناوب از بک‌اند می‌آیند. برای نمونه:

- هدف BOOLEAN روزانه، قرارداد خاص خود را دارد؛
- امتیاز RATING در محدودهٔ تعریف‌شده بررسی می‌شود؛
- مدت‌زمان متناسب با واحد و تناوب اعتبارسنجی می‌شود؛
- اهداف و مقدار عملکرد یک مفهوم واحد نیستند.

**فرانت نباید نسخهٔ مستقلی از این قواعد تعریف کند.**

**فعالیت‌های مرتبط با قابلیت‌های جدید**

طبق کاتالوگ گزارش‌شده:

- ACT002: نوشیدن آب؛
- ACT005: خواب کافی با واحد ساعت؛
- ACT007: مدیتیشن؛
- ACT008: تمرین تنفس.

در اتصال واقعی، فعالیت باید از طریق شناسه و کد معتبر و اسنپ‌شات برنامه پیدا شود؛ **نه با مقایسهٔ نام فارسی قابل‌ویرایش آن.**

### ۴.۵ ثبت عملکرد

صفحهٔ «کارهای امروز» از برنامه، فعالیت‌ها و تاریخ انتخاب‌شده تغذیه می‌شود.

کاربر برای هر فعالیت مقدار مناسب را وارد می‌کند. بک‌اند بررسی می‌کند:

- کاربر اجازهٔ ثبت دارد؛
- فعالیت به برنامهٔ مجاز او تعلق دارد؛
- برنامه در وضعیت مجاز است؛
- تاریخ معتبر و در محدودهٔ دوره است؛
- مقدار با نوع داده سازگار است؛
- محدودیت ثبت روزانه رعایت شده است.

**رفتار فعلی گزارش‌شده**

- روزانه: ثبت دوم همان فعالیت در همان روز، در سطح برنامه رد می‌شود.
- هفتگی و ماهانه: چند رخداد معتبر می‌توانند در چرخه جمع شوند.
- ویرایش یا حذف عملکرد نهایی، مسیر کاربری موجود ندارد.
- ثبت صفر با نبود ثبت متفاوت است.
- محدودیت صریح «فقط امروز و دیروز» هنوز در بک‌اند فعلی گزارش نشده است.
- فرم today پس از POST لزوماً PRG انجام نمی‌دهد؛ ارسال مجدد همان POST می‌تواند در تناوب‌های هفتگی/ماهانه رخداد تکراری ایجاد کند.

**قید روزانهٔ برنامه، معادل تضمین دیتابیس در برابر درخواست هم‌زمان نیست.**

## بخش پنجم — گزارش‌ها و موتورهای محاسباتی

### ۵.۱ تمام تب‌های گزارش

جوما طبق گزارش سورس، **۹ تب اصلی به‌علاوهٔ یک تب تحلیلی** دارد.

| تب | کاربرد |
|---|---|
| خلاصه | شمارش‌ها و نمای کلی دوره |
| تحلیل موفقیت | تحقق، پوشش، چرخه‌های فعالیت و وضعیت‌های محاسباتی |
| فعالیت‌ها | مقدار و هدف هر فعالیت |
| وزن | نمایش اهمیت نسبی مطابق قرارداد موجود |
| تقویم | هیت‌مپ دوره و نشانه‌های خلق |
| روند | سری روزانهٔ موفقیت |
| خلق | شاخص‌های حال، نمودار و ثبت‌های روزانه |
| مقایسه | مقایسهٔ دو دوره همراه با محدودیت‌های تفسیر |
| جزئیات | رخدادهای خام و تاریخ آن‌ها |
| گزارش تحلیلی | تحلیل‌های قابل‌انتخاب و ترکیب شاخص‌ها |

**پنج نوع گزارش تحلیلی**

- فعالیت‌ها؛
- خلق؛
- همبستگی؛
- روزهای هفته؛
- ترکیب آزاد شاخص‌ها.

فیلترها و زیرحالت‌های موجود باید حفظ شوند، از جمله انتخاب دوره، بازه، فعالیت، شاخص و دورهٔ مقایسه.

**وضعیت نصب کامل R2 روی تمام استقرارهای زنده نیازمند تأیید جداگانه است.**

### ۵.۲ تفاوت اصطلاحات محاسباتی

| اصطلاح | معنی |
|---|---|
| **مقدار واقعی** | عددی که کاربر با واحد فعالیت ثبت کرده است |
| **هدف** | مقدار هدف‌گذاری‌شده در اسنپ‌شات برنامه |
| **ثبت معتبر** | داده‌ای که قواعد ثبت را گذرانده و ذخیره شده است |
| **تحقق هدف** | نسبت یا قاعدهٔ محاسباتی مربوط به نوع فعالیت |
| **موفقیت کلی** | خروجی تجمیع موتور با درنظرگرفتن وزن و چرخه‌های واجد شرایط |
| **پوشش** | میزان وجود داده طبق تعریف موتور؛ نه لزوماً تحقق هدف |
| **ثبت‌نشده** | داده‌ای وجود ندارد؛ نباید خودکار صفر فرض شود |

برای فعالیت‌های عددی و زمانی، نسبت سادهٔ مقدار ÷ هدف بخشی از محاسبه است، اما **تمام موتور موفقیت به همین تقسیم محدود نمی‌شود**. چرخه، زمان شروع و بایگانی، وضعیت داده و نوع فعالیت نیز مؤثرند.

### ۵.۳ مواردی که موتور باید حفظ کند

- چرخهٔ روزانه، هفتگی و ماهانه؛
- چرخهٔ باز و بسته؛
- شروع ناقص یا بایگانی ناقص؛
- روزهای هنوز نرسیده؛
- دادهٔ ناکافی؛
- تنظیم نامعتبر؛
- رخداد روزانهٔ مبهم و تکراری؛
- جداسازی RATING طبق قرارداد موجود.

وضعیت‌هایی مانند موارد زیر فقط پیام تزئینی نیستند؛ بخشی از معنی خروجی‌اند:

```text
NO_DATA
NO_ELIGIBLE_CYCLES
INSUFFICIENT_DATA
AMBIGUOUS_DUPLICATE
```

فرانت باید معنی قابل‌فهم آن‌ها را نمایش دهد؛ نه اینکه برای پرکردن نمودار، همه را صفر کند.

### ۵.۴ دو شاخص متفاوت خلق

**شاخص خلقِ مثبت**

در لایهٔ تحلیلی شخصی:

- از شاخص‌های مثبت تشکیل می‌شود؛
- استرس در آن به همان شکل شاخص‌های مثبت جمع نمی‌شود؛
- مقیاس گزارش‌شدهٔ آن ۱ تا ۵ است.

**حال‌وهوای ترکیبی**

در بخش‌هایی از هم‌مسیر و گزارش تحلیلی:

- استرس با تبدیل معکوس وارد فرمول می‌شود؛
- شاخص‌های موجود طبق تابع مرجع لحاظ می‌شوند؛
- گردکردن و محدودسازی مشخص دارد؛
- مقیاس آن با شاخص قبلی متفاوت است.

**این دو خروجی نباید با یک عنوان یا یک مقیاس نمایش داده شوند.**

### ۵.۵ همبستگی و بینش

توابع همبستگی در بک‌اند موجودند. اما:

- داشتن ضریب همبستگی به معنی رابطهٔ علت‌ومعلولی نیست؛
- حداقل نمونهٔ قابل‌محاسبه در یک تابع، الزاماً حداقل نمونهٔ مناسب برای پیام شخصی معتبر نیست؛
- دادهٔ گمشده و سری ثابت باید طبق قرارداد تابع رسیدگی شوند.

نسخهٔ تجاری باید از همین ابزارهای معتبر استفاده کند، اما **قواعد تبدیل تحلیل به پیام کاربر، لایهٔ جدیدی است**.

### ۶.۲ زمان‌های متفاوت

این زمان‌ها نباید مخلوط شوند:

- **تاریخ انجام:** کاربر دربارهٔ چه روزی گزارش می‌دهد؟
- **زمان ثبت:** چه زمانی اطلاعات به سیستم رسیده است؟
- **زمان اصلاح:** اگر اصلاح مجاز باشد، چه زمانی انجام شده است؟
- **زمان قطعی‌سازی:** برای قابلیت آب، چه زمانی پیش‌نویس به عملکرد قطعی تبدیل شده است؟

در بک‌اند فعلی، همهٔ این مفهوم‌ها برای تمام داده‌ها فیلد مستقل ندارند. به‌خصوص پیش‌نویس و قطعی‌سازی آب، هنوز قابلیت جدیدند.

### ۶.۳ جریان فعلی ثبت عملکرد

```text
انتخاب تاریخ و فعالیت
        ↓
ورود مقدار
        ↓
ارسال فرم به PHP
        ↓
کنترل نشست، CSRF، مجوز و مالکیت
        ↓
اعتبارسنجی تاریخ، برنامه، نوع مقدار و محدودیت ثبت
        ↓
ذخیرهٔ رخداد
        ↓
نمایش نتیجه
        ↓
مصرف همان رخداد در داشبورد، گزارش و DTO مجاز هم‌مسیر
```

**اصل مهم**

صفحهٔ داشبورد و صفحهٔ گزارش نباید هرکدام یک نسخهٔ مستقل از عملکرد نگهداری کنند.

**چند نمایش از یک داده، مجاز است؛ چند منبع حقیقت برای همان داده، مجاز نیست.**

### ۶.۴ جریان فعلی ثبت حال

```text
پنج پاسخ + یادداشت اختیاری
        ↓
ارسال به بک‌اند
        ↓
اعتبارسنجی
        ↓
ایجاد یا به‌روزرسانی رکورد امروز
        ↓
نمایش وضعیت جدید
        ↓
به‌روزرسانی خروجی گزارش‌ها و دسترسی‌های مجاز
```

در نسخهٔ هدف، این جریان دیگر نباید پیش‌شرط اجباری استفاده از بخش‌های اصلی باشد.

### ۶.۵ نقش تقویم

توابع جلالی در بک‌اند موجودند. **ساخت تقویم دوم در فرانت یا پورت آن به JavaScript ممنوع است.**

بک‌اند باید اطلاعاتی مانند این‌ها را آماده کند:

- امروز و دیروز؛
- عنوان تاریخ؛
- نام روز؛
- روزهای ماه؛
- مرز دوره؛
- تاریخ مجاز ثبت؛
- دلیل غیرفعال‌بودن ثبت.

اعتبار نهایی هنگام دریافت درخواست دوباره بررسی می‌شود؛ غیرفعال‌بودن یک دکمه در مرورگر، کنترل معتبر سرور نیست.

**موضوع فنی باز:** یکسان‌سازی منبع «امروز» در هسته و هم‌مسیر؛ چون در گزارش‌ها، منطقهٔ زمانی پیش‌فرض سرور و Asia/Tehran صریح هر دو دیده شده‌اند.

## بخش هفتم — هم‌مسیر، نقش‌ها و حریم خصوصی

### ۷.۱ هم‌مسیر چیست؟

هم‌مسیر امکان ارتباط مجوزمحور میان کاربر و همراه را فراهم می‌کند. این ماژول بخشی از پوشش جوماست و نباید از نسخهٔ کامل، بی‌اجازه حذف شود.

**نقش‌ها**

- مراجع یا کاربر دریافت‌کنندهٔ همراهی؛
- همراه مجاز؛
- مدیر.

نقش عمومی حساب، ثبت همراه فعال و پرچم‌های مرتبط باید طبق بک‌اند معتبر بررسی شوند. **انتخاب نقش در فرانت، مجوز واقعی ایجاد نمی‌کند.**

### ۷.۲ جریان ارتباط

1. کاربر همراه را انتخاب می‌کند.
2. متن رضایت و حدود دسترسی را می‌بیند.
3. درخواست ایجاد می‌شود.
4. همراه درخواست را می‌پذیرد یا رد می‌کند.
5. فقط پس از فعال‌شدن ارتباط، داده‌های مجاز قابل‌مشاهده‌اند.
6. مجوزها و امکان قطع ارتباط طبق قواعد موجود مدیریت می‌شوند.
7. تاریخچهٔ وضعیت و تغییر مجوز نگهداری می‌شود.

### ۷.۳ مجوزهای گزارش‌شده

| مجوز | دسترسی |
|---|---|
| VIEW_SUMMARY | خلاصهٔ مجاز و وضعیت‌های کلی |
| VIEW_PROGRESS | پیشرفت و پوشش تجمیعی |
| VIEW_ACTIVITY_DETAILS | جزئیات مجاز فعالیت‌ها |
| VIEW_MOOD | شاخص‌های خلق و، در وضعیت فعلی، یادداشت خلق |
| CLIENT_CAN_MESSAGE_COMPANION | بخشی از کنترل پیام‌رسانی |
| COMPANION_CAN_MESSAGE_CLIENT | بخشی دیگر از کنترل پیام‌رسانی |

طبق آخرین گزارش، امکان ارسال پیام به روشن‌بودن **هر دو مجوز پیام** وابسته است.

**سهمیه‌های پیش‌فرض گزارش‌شده**

- مراجع: ۳ پیام در روز؛
- همراه: ۲۰ پیام در روز؛
- فاصلهٔ حداقلی پیام‌ها: ۵ ثانیه؛
- محدودیت درخواست مجدد: ۲۴ ساعت.

این‌ها **مقادیر گزارش‌شدهٔ سیاست** هستند؛ تنظیمات واقعی استقرار باید جداگانه تأیید شوند.

### ۷.۴ نکتهٔ حساس دربارهٔ یادداشت

در وضعیت فعلی، مجوز مشاهدهٔ خلق شامل **متن یادداشت** هم می‌شود.

این واقعیت باید در رضایت کاربر روشن باشد. جداکردن مجوز عدد خلق از متن یادداشت، **هنوز تصمیم محصولی نهایی ندارد**.

برای قابلیت‌های جدید نیز باید مشخص شود:

- همراه بینش‌های شخصی را می‌بیند یا نه؟
- بینش ساخته‌شده از خلق، زیر کدام مجوز قرار می‌گیرد؟
- وضعیت جوجه و پاداش شخصی است یا قابل‌اشتراک؟

**نباید از طریق یک بینش، داده‌ای افشا شود که خودِ دادهٔ پایه مجوز مشاهده ندارد.**

### ۸.۲ یافتهٔ امنیتی فوری

در مسیر بازیابی رمز، تغییر رمز بدون اثبات مالکیت حساب گزارش شده است.

**دربارهٔ سورس محلی، یافته مستند گزارش شده؛ دربارهٔ فعال‌بودن همان نقص روی هر استقرار عمومی، تأیید مستقل نداریم.**

رسیدگی باید:

- جدا از بازطراحی ظاهری؛
- با مجوز مشخص؛
- بدون آزمایش روی حساب واقعی دیگران؛
- و با روش بازیابی امن انجام شود.

وجود دامپ اطلاعات کاربران و فایل‌های نشست در فضای پروژه نیز خطر انتقال ناخواسته به بسته یا مخزن را ایجاد می‌کند.

### ۸.۳ دو برداشت نادرست که نباید وارد تصمیم فنی شوند

- **توکن CSRF نشستیِ قابل‌استفادهٔ مجدد، به‌خودی‌خود نقص نیست.** CSRF با ضدتکرار عملیات دو مسئولیت متفاوت است.
- **نبود `updated_at` برای رخداد افزایشی، الزاماً باگ نیست.** برای دادهٔ قابل‌ویرایش، باید راه معتبر تشخیص تغییر و نگهداری تاریخچه طراحی شود.

### ۸.۴ موقعیت دموی قبلی 7C

دموی ساخته‌شدهٔ قبلی:

- برای بررسی ظاهر و بعضی تعامل‌ها قابل‌استفاده است؛
- اما موتورهای تقویم، موفقیت، تحلیل و قواعد دامنه را به مرورگر منتقل کرده بود؛
- در چند محاسبه و جریان با PHP اصلی اختلاف داشت.

بنابراین:

***دموی قبلی 7C، مرجع بصری است؛ نه مرجع معتبر منطق و نه کد آمادهٔ انتقال به تولید.***

سبزبودن تست‌های Node آن، این ناسازگاری معماری را برطرف نمی‌کند.

**برنامهٔ متناسب → زندگی و فعالیت واقعی → ثبت صادقانه → مشاهدهٔ الگوها → تنظیم بهتر برنامه**

- بهتر نشان‌دادن حال برای گرفتن پاداش؛

### ۱۰.۸ رابطهٔ ثبت‌ها با مراقبت و پاداش

در نسخهٔ تجاری، مراقبت و پاداش باید از **دادهٔ معتبر بک‌اند** تغذیه شوند؛ نه از رویداد کلیک.

| رویداد | اثر مجاز |
|---|---|
| کاربر فقط صفحه را باز می‌کند | ثبت عملکرد یا پاداش جدید ایجاد نمی‌شود |
| کاربر راهنما را می‌بیند | صرفاً وضعیت راهنما تغییر می‌کند |
| مقدار آب را در پیش‌نویس تغییر می‌دهد | عملکرد قطعی و پاداش قطعی ایجاد نمی‌شود |
| ثبت معتبر ذخیره می‌شود | اثر مراقبتی طبق قاعدهٔ مصوب قابل‌اعمال است |
| درخواست قبلی دوباره ارسال می‌شود | اثر تکراری ایجاد نمی‌شود |
| ثبت حال امروز ویرایش می‌شود | نباید صرفاً به‌دلیل ویرایش، رشد تکراری ایجاد شود |
| ذخیره ناموفق است | پیام موفقیت، رشد یا پاداش صادر نمی‌شود |
| هدف فعالیت کامل می‌شود | تحقق هدف نمایش داده می‌شود؛ پاداش اضافه فقط در صورت وجود قاعدهٔ مصوب |

**تفاوت سه مفهوم**

این مفاهیم نباید یکی شوند:

1. **ثبت معتبر:** اطلاعات با رعایت قرارداد ذخیره شده‌اند.
2. **تحقق هدف:** مقدار ثبت‌شده نسبت به هدف، طبق موتور معتبر ارزیابی شده است.
3. **مشارکت منظم:** کاربر در روزهای مختلف به برنامه برگشته و مشارکت کرده است.

ممکن است یک ثبت معتبر، تحقق هدف نداشته باشد؛ مثل ثبت مقدار صفر یا انجام ناقص. ممکن است ثبت با تأخیر مربوط به دیروز باشد، اما مشارکت واقعی کاربر امروز رخ داده باشد.

قواعد رشد جوجه باید بعداً مشخص کنند از کدام مفهوم استفاده می‌کنند.

| نزدیک تولد | «نشانه‌های تازه‌ای پیداست؛ همراه کوچکت دارد آمادهٔ دیدار می‌شود.» |
| تولد | «همراه کوچکت از راه رسید. دوست داری چه اسمی برایش انتخاب کنی؟» |
| نام‌گذاری | «این نام از حالا همراه مسیر شماست.» |
| ثبت موفق | «ثبتت ذخیره شد؛ یک قدم از امروزت روشن‌تر شد.» |
| روز کم‌انرژی | «همان چیزی را ثبت کن که واقعاً تجربه کرده‌ای؛ لازم نیست امروز شبیه روزهای دیگر باشد.» |
| بازگشت | «خوش برگشتی. می‌توانی از همین‌جا ادامه بدهی.» |

**عبارت‌هایی که نباید استفاده شوند**

- تهدید به آسیب‌دیدن همراه برای وادارکردن کاربر به بازگشت؛
- «کاربر خوب» در برابر «کاربر بد» بر اساس عملکرد؛
- خطاب‌هایی مانند پدر یا مادر بدون انتخاب کاربر؛
- ادعای مراقبت درمانی یا نظارت لحظه‌ای؛
- وعده‌های قطعیِ بهترشدن زندگی یا سلامت روان.

## بخش یازدهم — قرارداد نهایی ثبت‌ها تا این مرحله

### ۱۱.۱ پنجرهٔ مجاز ثبت عملکرد — مصوب

| تاریخ انجام | ثبت جدید |
|---|---|
| امروز | مجاز، با رعایت سایر قواعد |
| دیروز | مجاز، با برچسب تأخیر |
| قبل از دیروز | غیرمجاز |
| آینده | غیرمجاز |

این‌ها **دو روز تقویمی** بر اساس زمان مرجع بک‌اند هستند، نه بازهٔ ۴۸ساعته بر اساس ساعت گوشی.

**قواعد تکمیلی**

- برنامه‌ریزی آینده مجاز است؛ ثبت عملکرد آینده نیست.
- سوابق قدیمی قابل‌مشاهده باقی می‌مانند.
- تناوب هفتگی یا ماهانه حذف نمی‌شود؛ تاریخ رخداد باید در محدودهٔ مجاز باشد.
- در مرز ماه، ثبت دیروز باید به برنامه و فعالیت همان روز مربوط شود.
- گارد تاریخ در بک‌اند اعمال می‌شود؛ غیرفعال‌کردن دکمه در فرانت کافی نیست.
- این سیاست نسبت به سورس گزارش‌شده تغییر دارد و هنوز روی تولید اجرا نشده است.

**موضوع باز:** اگر برنامهٔ دیروز بایگانی شده باشد، نسبت قانون «ثبت دیروز» با قفل بایگانی باید صریحاً تعیین شود. هیچ قفلی خودکار دور زده نمی‌شود.

### ۱۱.۲ ثبت حال — مصوب

- ثبت حال فقط برای **امروز** است.
- قابلیت ویرایش حال امروز که در بک‌اند موجود است حفظ می‌شود.
- ثبت حالِ روزهای گذشته از رابط جدید ایجاد نمی‌شود.
- ثبت حال اختیاری است؛ کاربر می‌تواند «بعداً» را انتخاب کند.
- نداشتن ثبت حال، به معنی خلق صفر، حال بد یا پاسخ ناقص ساخته‌شده توسط سیستم نیست.
- حذف اجبار ثبت حال، نباید با حذف کنترل ورود، مالکیت یا مجوز صفحات اشتباه گرفته شود.

**تجربهٔ فرانت**

مرجع تجربهٔ مرحله‌ای، A است:

1. حال کلی؛
2. انرژی؛
3. تمرکز؛
4. کیفیت خواب شب قبل؛
5. استرس؛
6. یادداشت اختیاری و پایان ثبت.

**دعوت پیشنهادی برای یادداشت**

***«اگر دوست داری، یک جمله از امروزت برای خودت نگه دار؛ کوتاه، واقعی و به زبان خودت.»***

یادداشت نباید شرط دریافت بازخورد یا شرط کامل‌شدن ثبت حال باشد.

### ۱۱.۳ معنای خواب — مصوب

عنوان سؤال:

***«خواب دیشبت چطور بود؟»***

توضیح کوتاه:

*«کیفیت خواب شب قبل را در نظر بگیر؛ نه تعداد ساعت‌هایی که خوابیدی.»*

**قرارداد زمانی**

رکورد خلق روز **D**، کیفیت خواب شب منتهی به همان روز را نگهداری می‌کند.

بنابراین:

- پاسخ سه‌شنبه دربارهٔ خواب دوشنبه‌شب تا سه‌شنبه است؛
- برای بررسی خواب شب قبل و فعالیت روز، نگاشت پایه به فعالیت‌های همان سه‌شنبه است؛
- کیفیت خواب با ساعت خواب، یک داده نیست؛
- معنای ثبت‌های تاریخیِ پیش از صریح‌شدن سؤال، بدون مدرک بازتفسیر نمی‌شود.

### ۱۱.۴ اصلاح ثبت اشتباه

**وضعیت فعلی بک‌اند**

طبق گزارش:

- عملکرد ثبت‌شده مسیر ویرایش یا حذف ندارد؛
- حال امروز قابل‌به‌روزرسانی است.

**تصمیم فعلی محصول**

- پیش‌نویس‌ها قبل از قطعی‌شدن قابل‌اصلاح باشند.
- ویرایش موجود حال امروز حفظ شود.
- برای عملکرد قطعی، قابلیت اصلاح جدید هنوز مجوز اجرایی ندارد.
- «اصلاح با حفظ سابقه» برای آینده قابل‌بررسی است؛ اما نباید به‌صورت دکمه‌ای بدون پشتوانه ساخته شود.

قابلیت اصلاح عملکرد، اگر تصویب شود، باید اثر خود را روی گزارش، بینش، جوجه و پاداش نیز تعریف کند.

## بخش دوازدهم — قرارداد مصوب «آب امروز»

### ۱۲.۱ تعریف قابلیت

مدل انتخاب‌شده:

**پیش‌نویس زندهٔ آب + ثبت قطعی روزانه**

کاربر در طول روز مقدار را اضافه یا اصلاح می‌کند. این تغییرات در بک‌اند ذخیره می‌شوند، اما تا قطعی‌سازی، **عملکرد نهایی نیستند**.

قطعی‌سازی از دو مسیر انجام می‌شود:

1. تأیید دستی کاربر؛
2. قطعی‌سازی خودکار پس از پایان روز.

**هر دو غیرقابل‌ویرایش‌اند.**

### ۱۲.۲ ارتباط آب با برنامه

آب از کتابخانه و برنامه حذف نمی‌شود.

- هدف از فعالیت آبِ داخل برنامهٔ همان دوره خوانده می‌شود.
- هدف دوم و مستقلی برای داشبورد ساخته نمی‌شود.
- کارت داشبورد و ردیف آب در «کارهای امروز»، دو نمایش از یک داده‌اند.
- شناسه و کد معتبر فعالیت استفاده می‌شود؛ نه جست‌وجوی صرفاً متنیِ نام «آب».
- تغییر کتابخانه نباید هدف اسنپ‌شات برنامهٔ در حال اجرا را مخفیانه عوض کند.

**محدودهٔ فعلی این قرارداد**

این قرارداد برای **آب روزانه با واحد لیوان** است.

اگر کاربر تناوب یا واحد دیگری تعریف کرده باشد:

- هدف آن خودسرانه به روزانه تبدیل نمی‌شود؛
- هدف هفتگی بر هفت تقسیم نمی‌شود؛
- رفتار خاص آن باید جداگانه تعیین شود.

### ۱۲.۳ وضعیت‌های دادهٔ آب

| وضعیت | معنی |
|---|---|
| **ثبت‌نشده** | کاربر هنوز مقدار معتبری برای این روز انتخاب و ذخیره نکرده است |
| **پیش‌نویس ذخیره‌شده** | مقدار در بک‌اند محفوظ است و هنوز در محدودهٔ زمانی مجاز قابل‌تغییر است |
| **تغییر ذخیره‌نشده** | آخرین تعامل هنوز پاسخ موفق بک‌اند ندارد |
| **در انتظار قطعی‌سازی** | روز بسته شده، ولی ثبت نهایی هنوز پردازش نشده است |
| **ثبت قطعی** | یک عملکرد معتبر نهایی ایجاد شده و مقدار قفل است |
| **خطای قطعی‌سازی** | پیش‌نویس حفظ شده، اما ثبت نهایی موفق نشده است |

این وضعیت‌ها نباید صرفاً با رنگ متمایز شوند؛ عنوان متنی روشن هم لازم است.

### ۱۲.۴ رفتار در طول روز

نمونه با هدف شخصی شش لیوان:

| زمان | مقدار انتخابی | نتیجه |
|---|---|---|
| صبح | ۱ | پیش‌نویس یک لیوان |
| ظهر | ۳ | به‌روزرسانی همان پیش‌نویس به سه |
| عصر | ۵ | به‌روزرسانی همان پیش‌نویس به پنج |
| پایان روز | ۵ | یک عملکرد قطعی پنج‌لیوانی |

مقدارها با هم جمع نمی‌شوند؛ پیش‌نویس، **مجموع اعلام‌شدهٔ همان روز** را نگهداری می‌کند.

**متن کارت**

**آب امروز**
**۵ لیوان — هدف شخصی: ۶ لیوان**

*«تغییراتت ذخیره شده‌اند؛ تا پایان امروز قابل‌تغییرند و سپس خودکار قطعی می‌شوند.»*

مقدار و وضعیت تأییدشده از بک‌اند دریافت می‌شوند.

### ۱۲.۵ قطعی‌سازی دستی

اقدام «ثبت نهایی» باید فرعی اما قابل‌دسترسی باشد؛ نه آن‌قدر برجسته که کاربر را به قفل‌کردن زودهنگام روز تشویق کند.

**پیام تأیید**

**عنوان:**

*«آب امروز را قطعی ثبت کنیم؟»*

**متن:**

*«برای امروز، ۵ لیوان آب ثبت می‌شود. پس از تأیید، امکان تغییر یا افزودن مقدار به ثبت آب امروز را نداری.»*

**توضیح:**

*«اگر ممکن است امروز باز هم آب بنوشی، پیش‌نویس را باز نگه دار؛ پایان روز خودکار ثبت می‌شود.»*

**دکمه‌ها:**

- «بله، ثبت قطعی»
- «فعلاً نه، قابل‌تغییر بماند»

تاریخ و مقدار داخل پیام باید از وضعیت معتبر همان عملیات بیایند.

پس از تأیید، فقط پاسخ موفق بک‌اند مجوز نمایش «ثبت قطعی شد» است.

### ۱۲.۶ قطعی‌سازی خودکار

**قرارداد مصوب**

با پایان روز:

- امکان تغییر پیش‌نویس همان روز بسته می‌شود؛
- آخرین مقدار با موفقیت ذخیره‌شده، مبنای ثبت نهایی است؛
- پس از ثبت قطعی، اصلاح یا افزایش مقدار مجاز نیست.

**تفاوت زمان بسته‌شدن با زمان پردازش**

ممکن است پردازش سرور دقیقاً در لحظهٔ تغییر روز اجرا نشود. بنابراین باید این دو زمان جدا باشند:

1. **پایان پنجرهٔ تغییر مقدار؛**
2. **زمان اجرای قطعی‌سازی.**

تأخیر پردازش نباید اجازهٔ تغییر پیش‌نویس بسته‌شده را بدهد.

همچنین این تأخیر فنی نباید به‌اشتباه «کاربر با تأخیر ثبت کرده» نام‌گذاری شود.

**نیاز فنی**

بک‌اند باید سازوکار قابل‌اتکایی برای:

- اجرای قطعی‌سازی؛
- جبران اجراهای انجام‌نشده؛
- تلاش مجدد؛
- جلوگیری از ثبت تکراری؛
- و بازیابی پس از خطا داشته باشد.

وجود این زیرساخت در برنامهٔ اصلی هنوز تأیید نشده است. تایمر مرورگر جایگزین آن نیست.

### ۱۲.۷ صفر، نبود داده و ثبت دیروز

| حالت | رفتار |
|---|---|
| هیچ پیش‌نویسی ایجاد نشده | ثبت خودکار صفر ممنوع است |
| کاربر صریحاً صفر را انتخاب و ذخیره کرده | صفر، مقدار معتبر پیش‌نویس است |
| دیروز ثبت قطعی دارد | تغییر مجاز نیست |
| دیروز پیش‌نویس بسته‌شده و منتظر پردازش دارد | مسیر ثبت تازه برای دورزدن آن باز نمی‌شود |
| دیروز نه پیش‌نویس دارد و نه ثبت قطعی | ثبت با تأخیر، طبق سایر قواعد برنامه، ممکن است |
| قبل از دیروز | ثبت جدید ممکن نیست |
| آینده | ثبت عملکرد ممکن نیست |

**روز جدید، پیش‌نویس جدید می‌خواهد.** مقدار دیروز نباید خودکار به امروز منتقل شود.

### ۱۲.۸ انیمیشن، صدا و بازخورد

**خواستهٔ محصول**

لیوان آب باید تجربه‌ای تصویری، زیبا و در صورت امکان صوتی داشته باشد.

**جزئیات پیشنهادی**

- پس از ذخیرهٔ موفق پیش‌نویس، سطح آب با موجی کوتاه بالا یا پایین برود.
- پیام «پیش‌نویس ذخیره شد» با «ثبت قطعی شد» متفاوت باشد.
- صدا قابل‌خاموش‌کردن باشد.
- پیشنهاد این سند: صدا پیش‌فرض خاموش باشد.
- صدا با بارگذاری صفحه، رفرش یا تغییر داده از تب دیگر پخش نشود.
- صداها هنگام تعامل سریع روی هم انباشته نشوند.
- حالت کاهش حرکت پشتیبانی شود.
- شکست انیمیشن یا پخش صدا، روی ذخیره‌سازی اثر نگذارد.

**اثر روی جوجه**

- پیش‌نویس، پاداش قطعی ایجاد نمی‌کند.
- اثر قطعی فقط بعد از ثبت نهایی معتبر اعمال می‌شود.
- قطعی‌سازی دستی پاداش بیشتری از قطعی‌سازی خودکار ندارد.
- مقدار دقیق اثر مراقبتی و سیاست پاداش صفر هنوز باید در فصل جوجه تصویب شود.

| **تنظیمات** | کنترل تجربه | پروفایل، ترجیحات موجود، تم و تنظیمات جدیدِ مصوب |
| **پروفایل** | مشاهدهٔ اطلاعات حساب | نمایش دقیق و مسیر روشن ویرایش |
| **درباره و پشتیبانی** | شناخت و دریافت کمک | محتوای رسمی و راه‌های ارتباطی واقعی؛ قابلیت نمایشی با برچسب مشخص |
| **خروج** | پایان استفاده | پایان نشست طبق قرارداد امن؛ بدون ازدست‌رفتن ثبت‌های قطعی |

### ۱۳.۳ گزارش‌ها؛ پوشش کامل و معنی‌دار

فرانت باید تمام بخش‌های موجود را پوشش دهد:

1. خلاصه؛
2. تحلیل موفقیت؛
3. فعالیت‌ها؛
4. وزن؛
5. تقویم؛
6. روند؛
7. خلق؛
8. مقایسه؛
9. جزئیات؛
10. گزارش تحلیلی.

در تب تحلیلی نیز پنج نوع گزارش موجود حفظ می‌شوند:

- فعالیت‌ها؛
- خلق؛
- همبستگی؛
- روزهای هفته؛
- ترکیب آزاد.

**قواعد نمایش**

- دادهٔ ناقص با صفر جایگزین نشود.
- شاخص خام، درصد تحقق و شاخص ترکیبی با عنوان مشترک نمایش داده نشوند.
- مقدار هدف با مقدار واقعی اشتباه گرفته نشود.
- «ثبت بیشتر» خودکار به معنی «فرد موفق‌تر» نیست.
- فرانت سری‌ها و برچسب‌های آماده را رسم کند؛ میانگین، پیرسون یا نرمال‌سازی مستقل نسازد.
- هشدارهای معتبر موتور، مانند چرخهٔ مبهم یا دادهٔ ناکافی، برای زیباترشدن صفحه حذف نشوند.

### ۱۳.۴ راهنمای قدم‌به‌قدم

**مصوب**

- راهنما در ورود اول پیشنهاد یا نمایش داده شود.
- کاربر بتواند «رد کردن راهنما» را انتخاب کند.
- با دکمهٔ «بعدی» مراحل را جلو ببرد.
- هر زمان خواست، راهنما را دوباره اجرا کند.
- راهنمای کاربر قدیمی با تازه‌وارد یکسان نباشد.

**جزئیات پیشنهادی**

- هر مرحله فقط یک بخش را برجسته کند.
- متن کوتاه، کاربردمحور و بدون اصطلاح فنی باشد.
- دکمه‌های قبلی، بعدی و خروج مشخص باشند.
- روی موبایل، باکس راهنما عنصر هدف را نپوشاند.
- راهنمای هم‌مسیر فقط امکانات مجاز همان نقش را معرفی کند.
- راهنما هیچ ثبت عملکرد، خلق یا پاداشی ایجاد نکند.
- بازکردن راهنما وسط فرم، اطلاعات واردشده را پاک نکند.

### ۱۳.۵ حضور کنترل‌شدهٔ کاراکتر

هدف، محیط دوست‌داشتنی است؛ نه پرکردن همهٔ قسمت‌ها با جغد.

**پیشنهاد طراحی**

- یک پیام اصلی از جوما در محدودهٔ فعال صفحه کافی باشد.
- تصویرک فعالیت‌ها می‌توانند شخصیت مستقل داشته باشند، اما جزئیاتشان در اندازهٔ کوچک خوانا بماند.
- پیام‌های راهنما، بینش و جشن هم‌زمان روی هم ظاهر نشوند.
- متن خطا باید ابتدا مشکل و راه ادامه را توضیح دهد؛ کاراکتر نباید وضوح آن را کم کند.
- هنگام ثبت حال، نوشتن یادداشت یا تنفس، اعلان غیرضروری ظاهر نشود.

## بخش پانزدهم — موتور بینش و دفترچهٔ جوما

### ۱۵.۱ سه نوع پیام، با سه معنای متفاوت

| نوع | مبنا | نمونهٔ عنوان |
|---|---|---|
| **یادآوری عمومی** | متن بازبینی‌شده، بدون ادعای تحلیل شخص | «یک یادآوری از جوما» |
| **بازخورد ثبت** | یک اقدام معتبر و تأییدشده | «ثبت امروزت» |
| **بینش شخصی** | تحلیل واقعی داده با شواهد | «از ثبت‌های تو» |

در روزهای اول، پیام‌های عمومی واقع‌بینانه می‌توانند ارتباط ایجاد کنند. اما نباید به‌عنوان «کشف دربارهٔ تو» معرفی شوند.

### ۱۵.۲ مسیر دادهٔ بینش

**ثبت معتبر → خواندن دادهٔ مجاز → محاسبه با ابزار بک‌اند → ارزیابی قاعده → ساخت بینش → ذخیره در بانک پیام → نمایش مناسب → نگهداری در دفترچه**

**آنچه موجود است**

طبق گزارش، ابزارهای سروری برای:

- سری‌های روزانه؛
- میانگین‌ها؛
- همبستگی؛
- آمار روز هفته؛
- نرمال‌سازی؛
- و خروجی‌های گزارش وجود دارند.

**آنچه جدید است**

- قواعد نسخه‌دار بینش؛
- شواهد قابل‌نمایش؛
- بانک ماندگار پیام؛
- وضعیت خواندن و بستن؛
- انقضا و جایگزینی بینش؛
- ترجیحات کاربر و محدودیت نمایش.

این لایهٔ جدید، مجوز ساخت موتور آماری موازی نیست.

### ۱۵.۳ شناسنامهٔ هر بینش

هر بینش باید بتواند به این سؤال‌ها پاسخ دهد:

- دربارهٔ کدام شاخص‌هاست؟
- از چه بازه‌ای استفاده کرده؟
- چند مشاهده یا جفت داده داشته؟
- دادهٔ ناقص چگونه کنار گذاشته شده؟
- نتیجه مربوط به همان روز است یا روز بعد؟
- قاعده و نسخهٔ آن چیست؟
- چه زمانی محاسبه شده؟
- آیا هنوز معتبر است؟
- کاربر قبلاً آن را دیده یا بسته است؟

**رابط شواهد**

کنار پیام:

**«این برداشت از کجا آمده؟»**

مثال متن مناسب:

*«در ثبت‌های این بازه، روزهایی که خواب بهتری گزارش کرده‌ای، پیاده‌روی بیشتری هم ثبت شده است. این همراهی به‌تنهایی علت را نشان نمی‌دهد.»*

نباید این متن تبدیل شود به:

*«خواب خوب قطعاً باعث می‌شود ورزش را کامل انجام بدهی.»*

### ۱۵.۴ محدودیت‌های بینش

- حداقل داده و آستانه‌ها هنوز نیازمند پیشنهاد فنی و بازبینی تخصصی‌اند.
- توانایی موتور برای محاسبهٔ یک ضریب، به‌تنهایی دلیل مناسب‌بودن نمایش آن به کاربر نیست.
- تعداد نمونه و عدم قطعیت باید قابل‌فهم باشند.
- روز بدون ثبت، لزوماً روز بدون فعالیت نیست.
- دادهٔ ساختگی دمو با برچسب مشخص استفاده می‌شود.
- یادداشت آزاد برای تولید پیام به سرویس بیرونی ارسال نمی‌شود، مگر در یک طرح آینده با رضایت و تأیید مستقل.
- هیچ بینشی تشخیص، ارزیابی ارزش فرد یا وعدهٔ درمان نیست.

### ۱۵.۵ تجربهٔ دفترچه

**مصوب**

- صفحهٔ مستقل «دفترچهٔ جوما» وجود داشته باشد.
- داشبورد فقط یک پیش‌نمایش کوچک از یک بینش مرتبط نشان دهد.
- کاربر بتواند همهٔ بینش‌های قابل‌دسترسی خود را مرور کند.

**پیشنهادی**

- فیلتر موضوعی ساده؛
- نمایش تاریخ و بازه؛
- دسترسی به شواهد؛
- بستن پیام یا اعلام «برایم مفید نبود»؛
- امکان کاهش یا خاموش‌کردن پیام‌های تحلیلی.

خوانده‌شدن نباید صرفاً با ساخته‌شدن HTML فرض شود. وضعیت نمایش، مشاهده، خواندن و بستن باید تعریف مشخص داشته باشد.

هماهنگ‌سازی زمان، تصمیم فنی کنترل‌شده است؛ نباید به تغییر مخفی موتورهای فروزن تبدیل شود.

## بخش هفدهم — هم‌مسیر، رضایت و حریم خصوصی

### ۱۷.۱ رفتار موجود قابل‌استفاده

طبق گزارش، هم‌مسیر دارای:

- نقش‌های مراجع، همراه و مدیر؛
- چرخهٔ درخواست، پذیرش، رد و قطع ارتباط؛
- رضایت نسخه‌دار؛
- مجوزهای مشاهده و پیام؛
- سهمیه و زمان انتظار؛
- خروجی‌های محدودشدهٔ DTO؛
- تاریخچهٔ مجوز و رویدادهاست.

این قابلیت‌ها نباید با یک مدل ساده‌تر مرورگری جایگزین شوند.

### ۱۷.۲ حساسیت یادداشت و دادهٔ مشتق

در وضعیت گزارش‌شدهٔ فعلی:

- مجوز مشاهدهٔ خلق، یادداشت خلق را هم شامل می‌شود.

در نسخهٔ تجاری باید صریحاً مشخص شود:

- آیا همین قرارداد حفظ می‌شود؟
- آیا متن یادداشت رضایت جدا می‌خواهد؟
- آیا همراه می‌تواند بینش‌های ساخته‌شده از خلق را ببیند؟
- آیا وضعیت جوجه و مشارکت، شخصی‌اند یا قابل‌اشتراک؟

**بینش مشتق‌شده نباید راه دورزدن مجوز دادهٔ اصلی باشد.** اگر همراه اجازهٔ مشاهدهٔ خلق ندارد، نباید از یک پیام تحلیلی، اطلاعات محدودشدهٔ خلق را دریافت کند.

تا تصویب قرارداد داده‌های مشتق، نمایش آن‌ها به همراه قطعی نیست.

### ۱۷.۳ موارد لازم پیش از انتشار تجاری

این موضوعات باید سیاست مشخص داشته باشند:

- نگهداری اطلاعات؛
- خروجی‌گرفتن کاربر از دادهٔ خودش؛
- حذف حساب و داده؛
- اثر حذف یا اصلاح بر گزارش و بینش؛
- دسترسی همراه پس از قطع ارتباط؛
- نگهداری یا حذف تاریخچه‌های رضایت و پیام؛
- پشتیبانی و رسیدگی به خطاهای داده.

الزامات حقوقی باید متناسب با بازار و نوع خدمت، توسط فرد متخصص بررسی شوند؛ این سند حکم حقوقی صادر نمی‌کند.

## بخش هجدهم — مسیر توسعهٔ آینده

### ۱۸.۱ تفکیک «پوشش کامل» از «ساخت همه‌چیز در یک مرحله»

پوشش کامل یعنی هیچ قابلیت معتبرِ داخل دامنه فراموش نشود. این به معنی انتشار یک‌بارهٔ همهٔ تغییرات نیست.

ترتیب اجرا می‌تواند مرحله‌ای باشد، ولی:

- دامنهٔ هر مرحله روشن است؛
- قابلیت باقی‌مانده ثبت می‌شود؛
- بخش ناقص با عنوان «کامل» تحویل نمی‌شود.

### ۱۸.۲ ترتیب پیشنهادی توسعه

| مرحله | هدف |
|---|---|
| **۱. تثبیت سند** | قواعد داده، تجربه، جوجه، بینش و معیار پذیرش |
| **۲. پیش‌نمایش تجربه** | ارزیابی فهم‌پذیری و ظاهر، بدون جعل رفتار محاسباتی |
| **۳. محیط مستقل بک‌اند** | اجرای توابع معتبر با دادهٔ ساختگی و ایزولاسیون واقعی |
| **۴. اتصال فرانت به خروجی معتبر** | پوشش جریان‌های اصلی و حذف موتورهای موازی |
| **۵. قابلیت‌های جدید بک‌اند** | پیش‌نویس و قطعی‌سازی آب، جوجه، بانک پیام و بینش |
| **۶. آزمون محصول و فنی** | کاربر واقعیِ آزمایشی، مرورگر، هم‌زمانی، خطا و مجوز |
| **۷. انتشار کنترل‌شده** | با تأیید جدا، امکان خاموش‌کردن و حفظ داده |
| **۸. توسعهٔ بعدی** | امکاناتی که پس از ارزیابی ارزش و نیاز تصویب می‌شوند |

رسیدگی به ریسک‌های امنیتی فوری باید مسیر موازی و جداگانه داشته باشد؛ منتظر پایان طراحی بصری نمی‌ماند.

### ۱۸.۳ قابلیت‌های قابل‌بررسی برای آینده

این فهرست **تعهد پیاده‌سازی نیست**:

- شخصی‌سازی آشیانه و مراحل رشد بعد از تولد؛
- اصلاح عملکرد با حفظ سابقه؛
- مرور هفتگی ساده و قابل‌فهم؛
- پیشنهادهای قابل‌تأیید برای برنامهٔ دورهٔ بعد؛
- تنظیم میزان حضور کاراکتر و پیام‌ها؛
- یادآوری واقعی با رضایت و کنترل کاربر؛
- خروجی داده و مدیریت حساب؛
- اتصال سنجیده به سامانهٔ آزمون‌ها یا نوبت‌دهی؛
- توسعهٔ بازار و منطقه‌های زمانی؛
- نسخهٔ نوجوانان.

**نسخهٔ نوجوانان**

ورود نوجوانان در مسیر آیندهٔ محصول پیش‌بینی شده است، اما نیازمند بررسی مستقلِ:

- محتوا و لحن؛
- رضایت و نقش سرپرست؛
- حریم خصوصی؛
- ارتباط با همراه؛
- پاداش و فشار رفتاری؛
- و جریان‌های مرتبط با حمایت و ایمنی است.

نباید نسخهٔ بزرگسال صرفاً با تصویرهای کودکانه‌تر به نوجوانان ارائه شود.

## بخش نوزدهم — معیارهای پذیرش نسخهٔ تجاری

### ۱۹.۱ تجربهٔ کاربری

نسخه باید با آزمون نشان دهد که:

- کاربرِ تازه‌وارد می‌فهمد جوما چه می‌کند؛
- بعد از ردکردن راهنما، قدم اصلی را پیدا می‌کند؛
- فرق پیش‌نویس، ثبت قطعی و تحقق هدف را می‌فهمد؛
- برای ثبت حال مجبور به ارائهٔ پاسخ ساختگی نمی‌شود؛
- پس از غیبت، امکان ادامهٔ محترمانه و ساده دارد؛
- جوجه را همراه می‌داند، نه ابزار فشار.

### ۱۹.۲ صحت داده

- صفر با نبود داده فرق دارد.
- امروز و دیروز در بک‌اند کنترل می‌شوند.
- عملکرد آینده پذیرفته نمی‌شود.
- حال فقط امروز ثبت می‌شود.
- آب یک منبع حقیقت دارد.
- قطعی‌سازی دستی و خودکار، ثبت تکراری ایجاد نمی‌کنند.
- خطای ذخیره، موفقیت ظاهری تولید نمی‌کند.
- گزارش‌ها از موتور معتبر تغذیه می‌شوند.
- تغییر قالب، رنگ یا نمودار معنی داده را عوض نمی‌کند.
- دادهٔ مجاز هفتگی و ماهانه به‌اشتباه تکراری تلقی نمی‌شود.

### ۱۹.۳ معماری و امنیت

- هیچ موتور دامنه‌ای به مرورگر منتقل نشده باشد.
- مجوزها و سهمیه‌ها در سرور اعمال شوند.
- دادهٔ غیرمجاز اصلاً به فرانت ارسال نشود.
- توابع موجود بدون دلیل موازی‌سازی نشوند.
- محیط دمو از تولید مستقل باشد.
- دارایی‌های بستهٔ تحویل فاقد دادهٔ واقعی کاربران، نشست و secrets باشند.
- مسیر بازیابی رمز ناامن در نسخهٔ تجاری باقی نماند.
- خاموش‌کردن قابلیت جدید، نیازمند حذف اطلاعات کاربران نباشد.

### ۱۹.۴ آزمون‌های لازم

| دسته | نمونهٔ آزمون |
|---|---|
| تقویم | کبیسه، مرز ماه، امروز/دیروز، عبور از نیمه‌شب |
| ثبت | صفر، رشتهٔ خالی، قفل روزانه، رخداد تکراری، تاریخ نامجاز |
| آب | حفظ پیش‌نویس، پایان روز، ثبت دستی، خطای قطعی‌سازی، retry |
| جوجه | یک‌باره‌بودن رشد و تولد، بازیابی وضعیت، اثر غیبت |
| بینش | داده کافی/ناکافی، تغییر داده، انقضا، شواهد و مجوز |
| هم‌مسیر | قبل/بعد پذیرش، قطع ارتباط، تغییر مجوز، سهمیه و cooldown |
| فرانت | موبایل، تبلت، دسکتاپ، کیبورد، فوکوس، شیشه، صدا و کاهش حرکت |
| پایداری | چند درخواست هم‌زمان، قطع ذخیره، بازیابی و عدم ازدست‌رفتن داده |

**تست اجرا‌نشده، «قبول» محسوب نمی‌شود.** رندر رشته‌ای در Node، HTTP 200 و بارگذاری فایل، جای آزمون عملکردی مرورگر را نمی‌گیرند.

## بخش بیست‌ویکم — روش استفادهٔ شخص ثالث از این سند

هر طراح، توسعه‌دهنده یا ایجنت باید این ترتیب را رعایت کند:

1. **واقعیت موجود را بشناسد:** برنامهٔ فعلی چه داده و قواعدی دارد؟
2. **مصوبه را پیدا کند:** دقیقاً کدام رفتار جدید تأیید شده است؟
3. **تابع معتبر را شناسایی کند:** کدام قابلیت از قبل در بک‌اند وجود دارد؟
4. **شکاف را مشخص کند:** فقط UI، رابط ارتباطی یا ماژول جدید لازم است؟
5. **تغییر را پیشنهاد دهد:** فایل‌ها، اثر روی داده، ریسک و روش خاموش‌کردن.
6. **معیار پذیرش را اجرا کند:** صحت و تجربه، جداگانه آزمایش شوند.
7. **گزارش صادقانه بدهد:** تکمیل‌شده، ناقص، نامعلوم و اجرا‌نشده تفکیک شوند.

**چهار ممنوعیت اصلی**

- تبدیل پیشنهاد باز به تصمیم قطعی؛
- بازنویسی موتور موجود فقط برای راحت‌ترشدن فرانت؛
- ساخت درصد، بینش یا موفقیت نمایشیِ بدون داده؛
- انتقال تغییرات به سایت زنده صرفاً به‌دلیل تأیید ظاهر پیش‌نمایش.

## بخش بیست‌ودوم — جمع‌بندی سند

جوما در وضعیت فعلی، یک محصول سروری برای برنامه‌ریزی دوره‌ای، ثبت عملکرد و حال، گزارش و همراهی رضایت‌محور است. نسخهٔ تجاریِ موردنظر قرار است همین پایه را **روشن‌تر، تصویری‌تر، دوست‌داشتنی‌تر و قابل‌اعتمادتر** کند.

مسیر مطلوب:

***برنامه‌ای متناسب با زندگی → ثبت راحت و صادقانه → بازخورد روشن → شناخت تدریجی الگوها → همراهی بلندمدت با جوما***

«گوی آبی جوما» و جوجه، لایهٔ داستانی این مسیرند؛ نه جایگزین صحت داده و نه دلیلی برای ایجاد فشار بر کاربر.

**مرجع محاسبه بک‌اند می‌ماند. فرانت، زبان قابل‌فهم و جذاب آن است.**
